# tunnel — коммерческий B2B tunnel SDK на Rust

Партнёры встраивают связность вашего продукта в свои приложения, но их трафик
должен выходить через *вашу* инфраструктуру: один токен на партнёра, один
виртуальный адрес на клиента, транспорт — QUIC «из конца в конец», который
посредник не может отличить от шума. Эту задачу решают три развёртываемые
части:

- **`tunnel-core`** — клиентский SDK (iOS / Android / Desktop / Python): пять
  управляющих методов, QUIC-сессия с пиннингом сертификата сервера,
  переподключение с экспоненциальной задержкой, миграция соединения при
  смене сети (RFC 9000 — VIP и плоскость данных переживают переключение
  Wi-Fi ↔ сотовая сеть).
- **`tunnel-server`** — сервер под Linux: B2B-аутентификация токенами,
  пул виртуальных адресов, Reaper неактивных сессий, ограничения полосы
  на клиента, горячее отзывание токенов через HTTP admin API и режим TUN
  с готовыми NAT-командами.
- **`tunnel-cli`** — SOCKS5-прокси для десктопа: любое приложение с SOCKS5
  идёт через туннель **без root и без TUN-устройства** — userspace-стек TCP/IP
  (smoltcp) превращает сырые IP-пакеты туннеля обратно в TCP-потоки.

Транспорт — QUIC (`quinn` + `rustls`) на `tokio`. Партнёр получает готовый
SDK: нативные библиотеки + биндинги Swift/Kotlin/Python в `dist/`
(см. **[INTEGRATION.md](INTEGRATION.md)** — интеграция занимает ~10 строк
кода на язык).

## Состав репозитория

| Крейт / файл | Назначение |
| --- | --- |
| `tunnel-proto` | Общий протокол: управляющие сообщения (bincode + префикс длины), фрейминг IP-пакетов для QUIC-датаграмм, разбор заголовка IPv4, проверка токенов за константное время, счётчики телеметрии |
| `tunnel-core` | **Ядро SDK** (`cdylib`/`staticlib`), FFI через `uniffi`: пять управляющих методов (`new`/`connect`/`disconnect`/`get_telemetry`/`set_status_callback`), QUIC-клиент с пиннингом сертификата, переподключение с backoff, миграция соединения, RTT-пинг, обмен пакетами по опросу |
| `tunnel-server` | Сервер: аутентификация токенами (файл/переменная окружения + admin API), пул виртуальных адресов с повторным использованием, Reaper неактивных сессий (45 с), лимиты полосы (token bucket, `client:token:10mbps`), таблица маршрутизации, Linux TUN, loopback-режим для CI |
| `tunnel-cli` | Десктопный клиент: SOCKS5-слушатель на `127.0.0.1:1080`, userspace-стек TCP/IP поверх пакетной плоскости туннеля, периодический отчёт о статусе/RTT/скорости — без root |
| `build_sdk.sh` | Сборка SDK одной командой: release-библиотеки + биндинги → `dist/` |
| `INTEGRATION.md` | Гайд по встраиванию с примерами (Swift / Kotlin / Python) |

## Быстрый старт (15 строк, на клиенте root не нужен)

```bash
# ── сервер (Linux, один раз): режим TUN; он печатает точные NAT-команды ──
TUNNEL_TOKENS="demo:demo-token" tunnel-server --listen 0.0.0.0:443 --env-tokens \
    --tun tunnel0 --pool 10.66.0.0/24 --server-name tunnel.example.com \
    --export-cert tunnel-root.der
sysctl -w net.ipv4.ip_forward=1                 # напечатаны сервером выше,
iptables -t nat -A POSTROUTING -s 10.66.0.0/24 ! -o tunnel0 -j MASQUERADE  # с реальными значениями

# ── клиент (macOS / Windows / Linux — обычный пользователь без привилегий) ──
tunnel-cli --server tunnel.example.com:443 --cert tunnel-root.der --token demo-token
# info: tunnel connected vip=10.66.0.2 mtu=1280
# info: tunnel is up; the SOCKS5 listener is opening on 127.0.0.1:1080
# info: tunnel stats status=connected ping=Some("41 ms") down=1.2 KiB/s ...

# ── любое SOCKS5-приложение теперь выходит через ваш сервер ──
curl --socks5-hostname 127.0.0.1:1080 https://ifconfig.me/   # покажет IP сервера
```

Встраивание SDK вместо CLI: `TunnelClient` + TUN-устройство платформы —
см. **[INTEGRATION.md](INTEGRATION.md)**.

## SDK: публичный API клиентского ядра

```text
TunnelClient(config)          создать клиент (конфиг валидируется сразу)
  .connect()                  запустить движок: подключение, ретраи, keepalive
  .disconnect()               корректная остановка (не блокирует)
  .get_telemetry()            bytes_sent, bytes_received, ping_ms (RTT)
  .set_status_callback(cb)    Connected { mtu, vip } / Reconnecting / Disconnected
  .send_packet(bytes) -> bool плоскость данных: TUN платформы → туннель
  .recv_packet(timeout)       плоскость данных: туннель → TUN платформы
  .on_network_changed()       подсказка о смене сети (Wi-Fi ↔ cellular)
```

Колбэк статуса доставляется из внутренних потоков ядра **без дубликатов**;
текущий статус приходит сразу после регистрации. Смена сети после разрыва
— это `Reconnecting`; `disconnect()` и постоянные ошибки (отклонённый токен,
несовместимая версия) — `Disconnected`. В `Connected{mtu, vip}` партнёр
получает параметры TUN платформы: MTU интерфейса и выданный сервером адрес
клиента (каждый исходящий пакет обязан нести `src = vip` — сервер проверяет
анти-спуфингом).

Конфиг: обязательные поля `server_host`, `server_port`, `auth_token`,
`pinned_server_cert_der`; остальные имеют рекомендованные дефолты на уровне
биндингов (Kotlin/Swift/Python), поэтому минимальная интеграция — четыре
параметра.

## Сборка и проверка

```bash
cargo test  --workspace      # 120 тестов: протокол, ядро, сервер, CLI + E2E
cargo build -p tunnel-core   # lib + cdylib (.so) + staticlib (.a)
cargo build -p tunnel-server # бинарник tunnel-server
cargo build -p tunnel-cli    # бинарник tunnel-cli

./build_sdk.sh               # SDK одной командой → dist/ (см. dist/README.md)
./build_sdk.sh --skip-tests  # пересборка без прогона тестов
```

`build_sdk.sh` собирает release-библиотеку, генерирует биндинги для всех трёх
языков одной командой (`uniffi-bindgen generate-all`), наполняет `dist/`
(`lib/<triple>/`, `android/{kotlin,jniLibs}`, `ios/`, `python/`) и пишет
`SHA256SUMS`. Если установлен таргет `aarch64-linux-android`, включается и
`arm64-v8a`; iOS-статическая библиотека собирается на macOS
(`aarch64-apple-ios`).

## Запуск сервера

```bash
# Файл токенов: одна пара "client_id:token[:mbps]" в строке, '#' — комментарий;
# необязательный суффикс ограничивает полосу клиента (token bucket).
cat > tokens.txt <<'EOF'
# партнёр "example"
example-ios: b2b-live-a1b2c3d4
example-android: b2b-live-e5f6g7h8:10mbps
EOF

# Производственный режим: TUN + экспорт сертификата для пиннинга на клиенте
tunnel-server --listen 0.0.0.0:4433 --tokens tokens.txt \
    --tun tunnel0 --pool 10.66.0.0/24 --mtu 1280 \
    --server-name tunnel.example.com --export-cert tunnel-root.der

# HTTP admin API (только loopback, защита X-Admin-Key):
#   POST   /tokens              {"client_id": "...", "token": "...", "mbps": 10}
#   DELETE /tokens/{client_id}  горячее отзывание — закрывает живые сессии
#   GET    /stats               счётчики сессий/пула/трафика
TUNNEL_TOKENS="ci-client:ci-token" tunnel-server --listen 127.0.0.1:4433 --env-tokens \
    --admin-listen 127.0.0.1:8080 --admin-key operator-secret

# Loopback-режим (без --tun, без CAP_NET_ADMIN): эхо только на адрес самого
# сервера — для проверки клиентов и CI.
```

Сессия, молчащая 45 секунд, собирается сервером (соединение закрывается,
адрес возвращается в пул); у лимитированных клиентов избыточные датаграммы
отбрасываются, а не ставятся в очередь.

## Перегенерация биндингов

Биндинги для всех языков генерируются **одной командой** (метаданные API
читаются из библиотеки; в release-профиле они вырезаны, поэтому генерация
идёт из debug-сборки — `build_sdk.sh` это уже учитывает):

```bash
cargo build -p tunnel-core
cargo run -p tunnel-core --bin uniffi-bindgen -- \
    generate-all --library "$CARGO_TARGET_DIR/debug/libtunnel_core.so" \
    --out-dir bindings            # → bindings/{kotlin,swift,python}/
```

Для одного языка используйте стандартный CLI uniffi: `generate --library <lib>
--language swift --out-dir <dir>`. Актуальные сгенерированные биндинги лежат
в `bindings/`; партнёру они поставляются через `dist/`.

## Non-Goals

Это сфокусированный туннель, а не универсальный VPN-фреймворк:

- **Не анонимный/публичный VPN-продукт.** Клиенты аутентифицируются
  B2B-токенами партнёров; регистрации пользователей, биллинга и captive
  portal нет.
- **Никакой динамической mesh-маршрутизации.** Один сервер на развёртывание;
  клиент получает один адрес из плоского IPv4-пула.
- **Никаких сменных транспортов.** QUIC с пиннингом сертификата — единственный
  транспорт; маскировка трафика под другой протокол — вне scope.
- **Без kernel-bypass оптимизаций.** MVP нацелены на партнёрскую пропускную
  способность на штатном `quinn`; io_uring/XDP — будущее.
- **Сервер не управляет фаерволом хоста** — он печатает точные команды
  `iptables`/`sysctl`, а не меняет систему оператора сам.

## Известные ограничения

- IPv6: фреймы `KIND_IPV6` принимаются, но маршрутизация v6 не реализована —
  в режиме TUN они пересылаются как есть, в loopback — отбрасываются.
- `tunnel-cli` резолвит доменные имена системным резолвером — DNS в этой
  версии не идёт через туннель (CONNECT с IP-литералом работает всегда;
  DNS-over-tunnel — в планах).
- Сервер не пересчитывает IP-чек-суммы (это работа стека); loopback-эхо
  переписывает только адреса в заголовке.
- Закрытая TCP-сессия висит в TIME_WAIT 10 секунд (граница smoltcp) —
  пространство эфемерных портов (16 384 портов) поглощает обычный прокси-трафик.
- Реальный TUN-цикл не прогоняется в CI (нет `CAP_NET_ADMIN`): TUN-путь
  покрыт компонентными юнит-тестами, E2E идёт через loopback-режим
  и межклиентскую маршрутизацию.
- Таргеты Android/iOS в дистрибуции ограничены средой сборки: `arm64-v8a`
  собирается при наличии NDK-таргета, iOS — на macOS (см. INTEGRATION.md).
- В планах: DNS-over-tunnel, ротация токенов/HMAC-выдача через партнёрского
  брокера, метрики в формате Prometheus, IPv6 data plane.
